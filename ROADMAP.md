# Roadmap

ng-hop is an agent skill that upgrades an Angular app one tested major at a time, with its UI libraries, and stops to ask when one blocks the next major.

## What the design protects

1. **A plan you can trust.** It never recommends a version it can't back up. It says "unknown" instead of guessing and never downgrades a library silently. *Gave up:* some reports look more cautious than they needed to.
2. **Safe to interrupt.** Each major gets its own commit, so a stop only costs the major in progress. *Gave up:* it won't start on a repo with uncommitted changes.
3. **Low upkeep.** It reads npm and Angular's Update Guide live, with no version tables, so a new Angular should work without a new release. *Gave up:* it needs a network connection.

Everything else gets ordinary care, but none of these three gets traded away for speed, install size or support for other agents.

## Decisions

- **Stop at the ceiling and ask (2026-11-04).** When a library blocks the next major, go as far as everything supports, commit that, and ask whether to wait, replace it or force it. *Why:* you still get a working upgrade, and nothing gets forced without your say. *Gave up:* a single run may not reach the target.
- **Judge libraries by peer range and publish date, never by version number (2026-11-04).** *Why:* on 2026-11-04, 13 of the 21 libraries checked that declare Angular 22 support had a version number that doesn't match Angular's (`@clr/angular` 18.5.0, `ag-grid-angular` 36.3.0). *Gave up:* nothing; the data is on npm.
- **Reject an old open-ended release instead of downgrading to it (2026-11-04).** `ngx-toastr` 19.1.0 accepts Angular 22 through `>=16.0.0-0`, but it predates Angular 22 and is older than the current 20.0.5. *Why:* "a version that accepts 22" would quietly downgrade to something nobody tested. *Gave up:* the rare case where that old release would have worked.
- **Name every moving library in one `ng update`, with no `--force` (2026-11-04).** *Why:* `ng update` checks peers against everything it's about to install, so naming them together passes the check. Proven on real apps, where a plain agent had used `--force` on three of four updates. *Gave up:* long commands.
- **Run the app at every major (2026-11-04).** *Why:* `marked` dropping a file breaks `ng serve` and the build, and on Angular 22 `ng serve` broke while the build and tests stayed green. *Gave up:* time per major.
- **Render with the system's Chrome from the command line, with no Puppeteer or Playwright (2026-11-04).** *Why:* the skill has no install step. *Gave up:* Chrome's log doesn't record a message's level, so a plain `console.error('oops')` goes unnoticed. Angular's own error handler and uncaught errors are caught. (The part about the log is superseded by the 2026-11-07 decision on the DevTools protocol.)
- **No runtime dependencies, with one vendored parser (2026-11-04).** Version ranges are the one thing too risky to hand-write, so `semver` is bundled into one file. *Why:* skills run from a plugin cache with no install step. *Gave up:* updating `semver` is a manual step, described in `scripts/vendor/VENDORED.md`.
- **Read the registry directly, and fall back to npm on an auth error (2026-11-04).** *Why:* a direct read takes under two seconds for a real app where `npm view` took 17 seconds for one package, and npm already holds any private-registry credentials. *Gave up:* a second code path, covered by a test with a registry that demands a token.
- **Never run npm through a shell, and validate names from `package.json` (2026-11-04).** *Why:* on Windows, a shell reads `>=` as a redirect, and a crafted dependency name could inject a command. `package.json` is untrusted input. *Gave up:* nothing.
- **Every printed command uses `npx --no-install` (2026-11-05).** *Why:* npm has an unrelated package named `ng`, and plain `npx ng` downloads and runs it whenever the project's CLI isn't installed. A security review flagged this on the patch path, and it applied to every major's command too. A test now fails on a bare `npx ng`. *Gave up:* longer commands.
- **A library that already names the major stays put (2026-11-04).** *Why:* an upgrade shouldn't change what it doesn't have to. *Gave up:* newer patch releases come later, by choice.
- **Parse the Update Guide as text, never by running it (2026-11-04).** *Why:* it's TypeScript from the network. *Gave up:* a small parser that fails loudly if the file's shape changes.
- **Evals run in clean headless sessions, and the grader rebuilds every result (2026-11-04).** *Why:* an agent's account of its own work is what an eval can't trust, so the grader reinstalls, builds, tests and runs the app itself. `claude plugin eval` can't run a build after a case, and refuses to grant Bash on Windows. *Gave up:* evals are slow, and they run by hand instead of in CI. (The part about CI is superseded by the 2026-11-06 decision below.)
- **A library that could stay moves when a sibling needs it newer (2026-11-04).** *Why:* `@angular/cdk` 20 accepts Angular 21, so it stayed, but Nebular 17 on Angular 21 needs cdk ^21, and the plan wrongly reported the app as blocked. An OpenCode run on a free model found this. *Gave up:* a little of the "change as little as possible" rule, only where a peer requires it.
- **When someone says an upgrade was interrupted and asks to finish, finish (2026-11-04).** Stash the leftovers and redo that major, without asking first. Changes nobody has explained still get a question. *Why:* the first version asked, and plain Claude did better by just finishing. Stashing keeps the leftovers recoverable. *Gave up:* a moment of extra caution, since the person already gave the answer.
- **Offer patch releases when already on the target major (2026-11-04).** *Why:* someone asking for "the latest" means it, and plain Claude did this where the first version said there was nothing to do. *Gave up:* nothing.
- **Audit the eval scores before believing them (2026-11-04).** The first run scored 100% against 67%, and much of that gap was the harness: it left out two tsconfig files, punished safe experiments in temp folders, and cut runs off at 10 minutes. Fixed, it was 100% against about 90%. *Why:* a benchmark that flatters the thing you built is worse than none. *Gave up:* the bigger number.
- **Stay a plain Agent Skill, with the Claude Code plugin as one way to install it (2026-11-04).** *Why:* OpenCode and GitHub Copilot read the same `SKILL.md` format and both scan `.agents/skills/`, so nothing in the skill needs to know which agent runs it. The first OpenCode run also found a real plan bug, so other agents are worth testing on purpose. *Gave up:* no agent-specific features, such as a dialog for the final question.
- **Library versions in eval cases come from the live registry (2026-11-04).** *Why:* an upgrade needs real packages. *Gave up:* cases expire when a library catches up, so they carry an as-of date, and `test/` holds the permanent versions on a fake registry.
- **Judge the existing angular-eslint alignment exception on eligible target-line releases (2026-11-05; superseded by the preferred-release clarification below).** A real pnpm plan falsely blocked `@angular-eslint/builder` because old releases had Angular peers and the current line did not. Historical metadata must not disable the known alignment rule. Explicit peers in the eligible line still govern; the installed-version floor still prevents downgrades. *Gave up:* nothing; this narrows the existing tooling exception rather than inferring compatibility for arbitrary peerless libraries.
- **Use the preferred eligible release's peers for aligned tooling (2026-11-05).** An older peer-bearing `angular-eslint` release inside the eligible line must not defeat the current release's alignment rule and select an older package group than the installed builder. The candidate's own explicit peers remain authoritative; ordinary peerless libraries get no inference, and the installed floor is preserved. *Gave up:* nothing; this completes the historical-peer fix without changing app dependencies to bypass it.
- **Keep pnpm's target CLI in control with a scoped execution transport (2026-11-05).** A clean native-Windows workspace's installed CLI bootstrapped under `node_modules`; pnpm added a temporary importer, then the target CLI refused the dirty tree. A live probe proved plain `pnpm dlx` can still redispatch to the old local CLI. `update.mjs` acquires the target CLI through pnpm's cache and scopes Angular's own version-dispatch control to that child. It checks Git, preserves peer checks, never retries or resets, and adds no dependency, global install or manager provisioning. npm/yarn/bun commands stay unchanged. A real Angular 20 to 22 run on pnpm 12 reproduced this at 21 to 22, and on patch releases too, so those use the transport as well. Adding `packages: ['.']` to `pnpm-workspace.yaml` doesn't prevent it. Angular merged a fix on 2026-06-09 (angular-cli#33303), but CLI 21.2.29 still does this, and that's the CLI that starts a 21 to 22 hop, so the transport stays while people are upgrading from 21. *Gave up:* one small Node transport script and pnpm's normal target-CLI download.
- **Decline undecided pnpm install scripts, and leave approving them to the person (2026-11-05).** pnpm 11 and newer exit 1 on every install until each script is decided. *Why:* declining is what pnpm already does, so no new code runs and the upgrade can carry on, and a real Angular 20 app installed, built, tested and ran with all four declined. Approving runs third-party code on every install, which is the person's call. *Gave up:* a small commit nobody asked for, and a stop if a check then fails because a script didn't run.
- **Refuse a pnpm catalog that holds Angular or TypeScript (2026-11-05).** *Why:* through Angular 21's CLI, `ng update` prints `Package @angular/core was not found on the registry. Skipping.` and exits 0, having moved the libraries and left Angular behind with no migrations run. Angular 22's CLI stops with an error. A plan that can't be carried out isn't one to trust. *Gave up:* catalog projects have to move those packages to plain versions first. Library entries in a catalog are only reported as unchecked. (Superseded by the 2026-11-07 decision on moving the catalog.)
- **Read `pnpm-lock.yaml` as text, and look above the app for a workspace root (2026-11-05).** *Why:* an app inside a pnpm workspace was reported as npm and given npm commands, and with nothing installed its versions came from the bottom of each range. The skill's promise that the plan reads the lockfile also wasn't true on pnpm. *Gave up:* lockfiles older than pnpm 9's format can fall back to `node_modules`.
- **Keep `peerDependencyRules` in the pnpm force recipe, though pnpm's docs deprecate it (2026-11-05).** A plain agent in the baseline pointed out the deprecation. *Why:* the documented replacement, `overrides` with `:peer`, fails with `ERR_PNPM_INVALID_SELECTOR` on pnpm 12.4.2 and 12.16.1, while `peerDependencyRules` works on both. *Gave up:* the recipe needs revisiting once a released pnpm accepts the new form.
- **Move a library pinned to one that moves, even with no Angular peer (2026-11-05).** Recording the README demo, `ng update` refused the plan's command, because `@nebular/eva-icons` 16 peers on `@nebular/theme` at exactly 16.0.0, and the plan only followed Angular peers. *Why:* a printed command that can't run isn't a plan to trust. *Gave up:* a full registry read for each such library, and a blocker when none of its releases accept the new version.
- **The README shows a real upgrade, recorded (2026-11-05).** VHS recorded Claude Code upgrading the `nebular-blocked` eval app in WSL, sped up 6× into `docs/demo/upgrade.gif`. `docs/demo/upgrade.tape` holds the setup. *Why:* it shows the stop at the ceiling, and a real build break, better than any description. Recording it also found a plan bug that no case had run into yet. *Gave up:* it has to be recorded again when the plan's output or the report format changes, and the banner shows the account's plan name.
- **Evals can run in GitHub Actions, started by hand, with the login out of reach of install scripts (2026-11-06).** A full batch takes 5 to 7 hours on one machine and fills it, so nobody could use that machine meanwhile. *Why this shape:* evals install real npm packages, and a `claude setup-token` token lasts a year with no documented way to revoke it. Deleting a variable isn't enough on Linux, because `/proc/<pid>/environ` keeps it, and the runner's own user has sudo and docker. So everything untrusted runs as a user with neither, and the login arrives on stdin and reaches Claude Code over a file descriptor. An install script could also make the agent hand the login over itself: on a real Claude Code with a fake key and a local listener, a planted project settings file redirected it, and so did an `env` block in `.claude.json` even with every setting source off. So evals load no setting sources, `.claude.json` is immutable, and the harness is root-owned. Results drop `.git`, because its config can run commands in whatever runs git on it, including the machine that downloads them. `evals/canary.mjs` tries all of this with a real agent before a batch spends anything. `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` stays off, because it forces the permission mode to `default`, so these runs would stop matching local ones. *Gave up:* Linux only, so a problem only Windows has shows only in `npm test`. (The part about running only when started is superseded by the 2026-11-07 decision on a weekly run.) Claude Code and pnpm are pinned and need bumping by hand. Outgoing network isn't limited, so an install script can still send out anything it can read. Regrading a downloaded result can't re-read git, so it uses the facts saved at the time.
- **Stop before a major that changes a library's license, and have the plan find it (2026-11-06).** The plan compares each moving library's license field, and the license files when the field only points at one, and warns ahead of the major. *Why:* three runs per case scored 100% with the skill, and that score was hiding the worst result in the batch. Five of six runs that ended on PrimeNG 22 moved the app onto a commercial license without a word, while plain Claude mentioned it every time, because it read more of the test output. The skill had made agents trust a plan that said nothing, and no check looked for it. *Gave up:* a tarball download per major for a library whose field says `SEE LICENSE IN`, and a stop on an upgrade that would have built. Shared packages such as TypeScript aren't compared, since they'd need a very large registry read each. A banner from a package the plan doesn't move is still only caught if someone sees it. (The part about shared packages is superseded by the 2026-11-07 decision on what a library brings.)
- **Keep an installed open-ended library, and name the newer one (2026-11-07).** When no release names the major and the installed one still accepts it, it stays, marked UNCONFIRMED, with the newer version named in case the app needs it. *Why:* the plan moved AG Grid from 34.3.1 to 36.3.0, swapping one open-ended range for another, and bringing two majors of its own changes and 190 kB nobody asked for. AG Grid's own table says 28 and up work on Angular 22. Plain Claude read that table and stayed, and one run with the skill told the person 34.3.1 wouldn't work, which was false. *Gave up:* the library runs on a release older than the Angular major, so a break shows up in the checks instead of being avoided up front.
- **Read the answers as well as the score, with someone who didn't write the checks (2026-11-07).** After the license fix, the score was 100% again, so a fresh agent compared what each setup told the person. It found that the skill never mentioned a library's new required peer (0 of 9, against 9 of 9 for plain Claude), never mentioned Angular 22's higher Node minimum (0 of 18, against 1 of 18), and once said nothing used a library after cutting a file short with `head`. Each is now in the plan, the skill or a check. *Why:* the checks can only catch what someone thought of, and the two worst findings so far came from reading. *Gave up:* one more pass per benchmark. It still isn't proof: 100% means passing every check written so far.
- **Score both setups on the same checks, with results and process apart (2026-11-07).** The README counts only the checks both setups get, and splits what the person ends up with from how the work was done. *Why:* checks that only apply with the skill, such as whether it loaded, made the skill's total bigger, and process checks reward commits nobody asked plain Claude for. Counted that way, plain Claude gets 95% of the results, and that's the honest gap. *Gave up:* one big headline number.
- **Check the licenses of what a moved library brings, through one release's manifest at a time (2026-11-07).** New dependencies of a moved library, dependencies whose range changed, and shared packages such as TypeScript all get compared, with one note per library. *Why:* PrimeNG 22 brings six packages that also moved off MIT, including a license manager, and the plan only compared PrimeNG. The registry serves one release's manifest for a few kilobytes, where a whole document can run to megabytes, which is what kept shared packages out before. *Gave up:* a few small requests per moved library, and still nothing for a package the app lists that no moved library brings, such as `@primeuix/themes`. The skill checks companion packages by hand.
- **Name a deprecated framework package once, at the first major that installs it (2026-11-07).** *Why:* `ng update` moves `@angular/animations` along with core, so its deprecation from 20.2 on showed nowhere, and the person ends up on a package with no future without being told. *Gave up:* one small request per framework package the app lists, per major.
- **`--next` aims at Angular's `next` tag, and only when someone asks (2026-11-07).** *Why:* the tag is a minor of the current major or a prerelease of the next, depending on the month, so it moves within the major like a patch or takes a hop of its own, where libraries may use their own prereleases, stable releases first. The command names the prerelease exactly, because `@angular/core@23` would resolve to a stable 23. *Gave up:* nothing for anyone who doesn't ask, since the skill never uses it unprompted.
- **Read Chrome over the DevTools protocol, through a pipe (2026-11-07).** *Why:* Chrome's log doesn't record a message's level, so a plain `console.error('oops')` passed and the word ERROR in an ordinary log line failed. `--remote-debugging-pipe` gives the protocol over two file descriptors, so it needs no WebSocket, which Node 18 lacks, and no library. It now waits for the root to fill instead of a fixed virtual-time budget. *Gave up:* about two seconds more per check, and fifteen when an app never renders.
- **Move a pnpm catalog in the pnpm runner, around Angular's own update (2026-11-07).** `update.mjs` copies the catalog's versions into `package.json`, runs `ng update` as usual, writes the new versions back into the catalog, puts `package.json` back on `catalog:` and reinstalls. *Why:* Angular's CLI can't change a catalog, and `pnpm update` can't either: on pnpm 12.16.1 it replaced `catalog:` in `package.json` with a plain version. Plain Claude moved a catalog by hand and passed. Going around `ng update` instead of replacing it keeps its peer checks and migrations. *Gave up:* it edits `pnpm-workspace.yaml` as text, so it reads block-style catalogs only, and refuses anything else before changing a thing. A catalog other projects share moves them too, so the plan names them and the skill asks.
- **Run the question cases weekly, with the skill only (2026-11-07).** *Why:* the cases read the live registry, so the right answer changes when a library catches up, and nobody would notice until a full batch. A failed check with the skill fails the run, and GitHub emails whoever last changed the schedule. It costs about $1.50 of usage a week. *Gave up:* the upgrade cases and the baseline stay manual, since a full batch costs about $32.
- **Scripted upgrades with no agent cover Windows, yarn, bun and pnpm catalogs (2026-11-07).** `evals/hop.mjs` takes a fixture through the plan's own commands and checks the build, tests and running app after every major. It needs no login, so it runs on every change to the scripts and weekly. *Why:* it found five real problems in its first day, among them pnpm 12's native binary on Windows and yarn 4 stalling while installing Angular's temporary CLI, none of which the Linux agent evals could see. *Gave up:* it follows the plan's commands rather than an agent's judgement, so it tests the scripts, not the skill's instructions.
- **OpenCode and Claude Code on Windows run on the owner's machine, not in CI (2026-11-07).** *Why:* OpenCode's free models refused GitHub's runners with `FreeUsageLimitError` and a 21-hour wait. A paid key, like Claude Code's login on Windows, would sit where an install script can read it: OpenCode only takes keys from its environment or config, and Windows lets a process read the memory of another of the same user, with nothing like Linux's Yama to stop it. *Gave up:* those runs need the owner's say-so and a machine with memory to spare. The harness still runs OpenCode, with `--agent opencode`.
- **Keep the version `ng update` picks inside a peer range (2026-11-08).** For a shared package the plan names the smallest move, while `ng update` takes the newest release the peers allow, such as TypeScript 5.9 where the plan said 5.8. The plan now prints the range, and anything inside it stays. *Why:* going back to the plan's pick fights `ng update` and costs a reinstall, and on readme-wizard an agent installed a package the re-run plan no longer listed. *Gave up:* the smallest possible move, for shared packages only. A library `ng update` takes a major further than the plan is reported, and the plan checks the license of the newest release that fits as well as its own pick.
- **M7's internal libraries live in their own repo and reach the app through a private registry (2026-11-08).** A local Verdaccio on the Windows host stands in for a company's Artifactory or GitHub Packages. *Why:* "upgrade the libraries first" only means something when they're published separately, and that's how teams with shared UI libraries usually work. *Gave up:* the monorepo case, where `ng update` moves the libraries and the app in one go.
- **M7's video is built with HyperFrames from the real run (2026-11-08).** Its terminal output, diffs and screenshots go into HTML scenes rendered to video, with a synthetic voice, captions and chapters, about 8 to 10 minutes, and short asides for newer and more senior developers. *Why:* it shows what really happened, and a scene can be fixed and rendered again without re-recording. *Gave up:* a live screen recording's feel.
- **A scope with a registry of its own marks a library as the team's (2026-11-08).** *Why:* that's how a company publishes its packages (`@acme:registry=...`), and npm's own config already says it, so the plan keeps no list. *Gave up:* a company that serves everything, its own packages too, from one default registry gets no such hint.
- **The skill raises a Node pin the repo carries (2026-11-08).** A dev container, `.nvmrc`, `engines` field or CI workflow below the new Angular's range is raised in that major's commit. *Why:* those are the team's machines, and the upgrade would pass here and fail there. M7's dev container pins Node 22.12, which Angular 22 refuses. *Gave up:* a change outside the app's code that nobody asked for, so it's named under hand fixes.
- **The enterprise example lives in `examples/enterprise/`, as templates a setup script copies out (2026-11-08).** *Why:* the tutorial needs two repositories and a registry, which can't sit as git repositories inside this one, and anyone can rerun it from a clone. *Gave up:* the evals don't run it yet. A case could, with the registry started in CI.
- **No unit test running stops the run, like a failing build (2026-11-08).** *Why:* on readme-wizard, one spec that didn't compile stopped Karma before any of its 20 specs ran, at the start and after all four majors, and the report called it one failing test. *Gave up:* one more question, on apps whose tests were already broken.

## Milestones

### M5: 0.2.0, real apps, OpenCode, Windows and evals that keep up

The evals use small apps built for them, run on Linux, and only when someone starts them. This release is about apps nobody built for a test, another agent, Windows, and noticing when a library catches up.

- [ ] Take my own apps on old majors (`readme-wizard`, `pr-sweep`) to the latest Angular with the skill, and fix what that finds. Both upgrades are open for review, as pr-sweep #4 and readme-wizard #1. What they found:
  - [x] The app check never saw the dev server's errors once it was ready, and a `PORT` in the shell moved Angular 22's dev server.
  - [x] Line endings: each run wrote its own script to restore them, and one dropped a final newline, so the skill ships one.
  - [x] No test signal: an app with no `test` target runs the project's own test command, and a run where no test can run at all stops to ask.
  - [x] The report: release notes from the repository when a package ships none, the version `ng update` chose inside a range, and only the optional migrations that would change the app.
  - [x] Check the files `angular.json` loads from a library against its next release, so a dropped file such as `marked.min.js` shows in the plan instead of the build.
  - [ ] Record the README demo again, since the plan's lines changed (`fits`, `repository`), as its 2026-11-05 decision says.
- [x] Take a whole upgrade through OpenCode, and update the README's agent table with what happened. OpenCode 2.2 on a free model took the test app from Angular 20 to 22 on Windows, one commit per major, and passed all 17 checks.
- [ ] Answer every upgrade problem someone files, with the plan's output and a fix or a reason.
- [x] Evals on a schedule, so a library catching up shows as a changed result. A full batch costs about $32 of usage, so the weekly run covers the question cases, with the skill only.
- [x] Evals on Windows. Only `npm test` runs there today, so a problem only Windows has shows up nowhere else. The plan's real commands now run there on every change to the scripts. An agent on Windows runs on the owner's machine only.

**Done when:** both apps are on the latest Angular through the skill, the README's agent table says what OpenCode really did, a scheduled run has reported, and real upgrades have run on Windows.

### M6: 0.3.0, fewer stops

Each of these is a place where the skill stops or says less than it could today.

- [x] Take a pnpm catalog through an upgrade instead of refusing it. Angular 22's CLI lists the steps: edit the catalog, `pnpm install`, then `ng update <package> --migrate-only --from <old version>`. Plain Claude did this and passed.
- [x] Real yarn and bun fixtures. The plan prints their commands, but no real upgrade has run on either. Both now pass from Angular 20 to 22.
- [x] Say when a framework package the app uses is deprecated. `@angular/animations` is, from Angular 20.2 on, in favour of `animate.enter` and `animate.leave`.
- [x] Check the licenses of what a moved library brings with it: shared packages the plan moves, and new dependencies, such as `@primeui/license-manager` with PrimeNG 22.
- [x] A `--next` mode, for trying a prerelease Angular. Angular's `next` tag can be a new major or a minor of the current one, so it has to handle both.
- [x] See every console error in the app check, through Chrome's DevTools protocol instead of its log. Today a plain `console.error('oops')` goes unnoticed.

**Done when:** the catalog, yarn and bun cases pass in the evals with and without the skill, scored like the rest, `--next` plans a real prerelease, and the app check fails on a plain `console.error`.

Met on 2026-11-08. With the skill: yarn 16/16, bun 16/16 and the catalog 14/14, once the grader read a catalog's commits right. Without it: 11/15, 11/15 and 11/13, mostly no commits and the work left on main. `--next` planned Angular's real `22.3.0-next.4` on an app at 22.2.5, and the app check's tests fail on a plain `console.error` in Chrome.

### M7: 0.4.0, an enterprise upgrade, on video

A company's app is rarely one package. This release takes one built like the real thing from Angular 21 to 22, and turns the run into a tutorial. The video is for developers who are new to agentic coding but not to development, and should still work for juniors and seniors.

- [x] A fixture: an Angular 21 app on the pnpm toolchain, with internal UI libraries whose peer ranges stop at Angular 21, so they have to reach 22 before the app can. It's `examples/enterprise/`: `acme-ui`, `acme-portal` and a local registry.
- [x] Set up for a dev container, and upgraded from the Windows host, not inside the container. Rebuilt afterwards, the container runs Node 22.23.4, builds the app and serves it.
- [x] When a blocking library belongs to the person, offer to upgrade it first, in dependency order, besides waiting, replacing or forcing.
- [x] Take it to Angular 22 with the skill: the libraries first, then the app. Claude Code did it in six turns from the Windows host, for $7.62. What it ran into, and what the skill learned from it:
  - pnpm 12 holds back a release younger than its minimum release age, 24 hours by default, so the libraries' new 22.0.0 couldn't be installed at first. Claude Code's own safety check stopped the agent from relaxing that, and it asked. The troubleshooting guide covers it now.
  - Even exempted, the release still failed `ng update`, which applies the same age rule in its own resolver and ignores the exemptions. The agent found that in the Angular CLI's source, installed the exempted releases first and then updated Angular, with approval. The guide covers that too.
  - The agent missed the dev container's `FROM node:22.12.0`, and the container then refused Angular 22. The plan now names the repo's own Node pins below a major's range, wherever the repo keeps them.
- [ ] Make a video tutorial from that run.

**Done when:** the skill takes the libraries and then the app to Angular 22 from the Windows host, the dev container still builds and serves the app afterwards, and the video is made.

## Not planned

- **AngularJS (1.x) migrations.** That's a rewrite, and other skills cover it.
- **Adopting signals, standalone or new control flow.** Angular's own schematics do this, and mixing it into an upgrade makes the diff unreadable.
- **Replacing a library automatically.** That's a project with its own decisions, so the skill only gives you the facts.
- **Nx automation.** Nx has `nx migrate`. The plan flags Nx and still gives library facts.

## How we'll know it works

- The with-and-without benchmark shows a gap on the things this skill exists for, and it says so where there's none.
- Issues from people whose real apps it stopped or broke, which `.github/ISSUE_TEMPLATE/` asks for.
- It takes my own apps on old majors (`readme-wizard`, `pr-sweep`) to the latest Angular.
